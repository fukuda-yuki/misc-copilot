# ACCEPTANCE — 移行後の受入条件（要求の正本）

この文書は、BookCatalog を **.NET 10 / ASP.NET Core MVC / EF Core SQLite** へ移行したアプリが
「完成した」と言えるための条件を定めます。

- このサンドボックスが仕様として定め、**移行したアプリで確認**します。
- この文書には**実装方法や完成コードの断片を書きません**。どう実現するかは移行する人が自分で考えます。
- 受入条件を実装に合わせて黙って弱めることは禁止です。矛盾を見つけたら根拠を示し、その部分だけ解決を求めます。

## 判定の区分（凡例）

各条件には、根拠の種類を明記します。

| 区分 | 意味 |
| --- | --- |
| **【旧版ソース読解】** | 旧版のソースコードを読んで確認した**既存動作**。旧版で実際に動かして確認したものではない（旧版はこのサンドボックスでは未起動）。 |
| **【今回の追加要求】** | この移行サンドボックスのために新しく定めた要求。旧版には無い、または旧版と意図的に変える内容。 |
| **【検証の証拠】** | 確認の進め方と記録に関する要求。 |

「旧版ソース読解」と書いてあっても、**旧版で実測済みという意味ではありません。**

## このサンドボックスで意図的に変える点（重要）

1. **SQL Server / LocalDB を SQLite へ変える。**
   旧版は SQL Server LocalDB と `BookCatalog.mdf`（`|DataDirectory|`）を使う構成です。
   移行後はローカルの**実ファイルのSQLite**を使い、Docker・コンテナー・SQL Server・LocalDB・Azure を使いません。
2. **このサンドボックス専用の新しいDBを作る。**
   旧SQL Serverのデータの移送や、旧DBとの共有は今回の範囲に含めません。
   ただし初期データは旧版の seed と同じ7件（Active 6件、非Active 1件）を使います。
3. **seed の再投入を防ぐ。**
   旧版は起動時に `Books` が空だと7件を入れ直しますが、移行後はそれを**行いません**。
   利用者が追加・編集・削除した結果を取り消さないことを優先します。
   これは旧版からの**意図的な変更**です。

## A. 基本動作

### 1. ビルドと起動 【今回の追加要求】【旧版ソース読解】

- ASP.NET Core MVC のアプリとして、`net10.0` を対象に**ビルドでき、起動できる**こと。
- Entity Framework Core の SQLite provider を使うこと。
- 確認すること：対象フレームワークが `net10.0` であること、ビルドが成功すること、実際にプロセスとして起動しHTTPで応答すること。

### 2. 画面と既存CSS 【旧版ソース読解】

- 「一覧」「詳細」「追加」「編集」「削除確認」の画面が使えること。
- 既存のスタイル（旧版の `Content/Site.css` と、それを参照するレイアウト）が適用されること。
- 旧版の画面構成（一覧の表、追加/編集フォーム、詳細表、削除確認、共通レイアウトのヘッダー・ナビ・フッター）に対応する画面があること。

### 3. 一覧の絞り込みと並び順 【旧版ソース読解】

- 一覧は `IsActive == true` の書籍だけを表示すること。
- `Title` の**昇順**で表示すること。
- **SQLite で採用した照合順序（collation）を記録すること。**
- SQL Server と全言語・全文字の並びが完全一致することは**要求しません**。
  日本語などを含む場合の並びは、採用した照合順序での結果を記録すれば足ります。

### 4. 非Activeの扱い 【旧版ソース読解】

- 非Activeの書籍（例：初期データの "The Matrix: The Shooting Script"）も、**IDを指定した詳細・編集では扱える**こと。
- 非Activeにすると一覧から消え、Activeへ戻すと一覧へ復帰すること。

### 5. 追加とID採番 【旧版ソース読解】

- 有効な書籍を追加でき、**IDが採番**されること。
- 採番されたIDで、詳細・編集・削除ができること。

### 6. 削除と存在しないIDの扱い 【旧版ソース読解】

- 削除は**確認画面の後のPOST**でレコードを削除すること。
- 存在しないIDへの「詳細」「編集」「削除確認」の **GET は 404** になること。
- 存在しないIDへの**削除POSTは、旧版どおり一覧へのリダイレクト**であること。
  **あらゆる不明ID操作を一律404にしてはいけません。**

### 7. 日本語データ 【今回の追加要求】

- 日本語を含む `Title` / `Author` を保存し、読み直せること（文字化けしないこと）。

## B. 入力と作成日時

### 8. Title 【旧版ソース読解】

- 必須。最大200文字。
- 200文字は許可、201文字は拒否されること（境界値で確認）。

### 9. Author 【旧版ソース読解】

- 必須。最大100文字。
- 100文字は許可、101文字は拒否されること（境界値で確認）。

### 10. ISBN 【旧版ソース読解】

- 任意。最大13文字。
- **「必ず13桁」「数字のみ」「チェックディジット検証」といった仕様を追加しないこと。**
  旧版にあるのは最大長だけです。

### 11. PublishedYear 【旧版ソース読解】

- 任意（未入力を許可）。値があるときは 1800〜2100 の範囲であること。
- 1800 と 2100 は許可、1799 と 2101 は拒否されること（境界値で確認）。
- **未入力を 0 に変換しないこと**（未入力は「値なし」として扱う）。

### 12. サーバー側の検証 【今回の追加要求】

- 必須・長さ・範囲の検証は**サーバー側でも**行い、無効なPOSTを保存しないこと。
- **SQLiteの列型に長さを書くだけで検証したことにしないこと。**
- クライアント側の検証（`required`、`maxlength`、`min`/`max`）だけに依存しないこと。

### 13. CreatedDate 【旧版ソース読解】【今回の追加要求】

- 追加時に**サーバーが設定**すること。
- 編集では保持されること（編集で変わらないこと）。
- 旧版の `DateTime.Now`（ローカル時刻）の意味を、**説明なくUTCへ変えないこと**。
  UTCへ変える場合は、その判断と理由を記録すること。
- 編集のPOSTに別の `CreatedDate` を含めても、**既存値を上書きしないこと**。

### 14. antiforgery保護 【旧版ソース読解】

- 追加・編集・削除のPOSTにある **antiforgery 保護を保つ**こと。
- テストを通すために、保護や入力検証を**無効にしないこと**。

## C. SQLiteとデータの寿命

### 15. 実ファイルのSQLiteを使う 【今回の追加要求】

- **実ファイルのSQLite**を、通常のアプリ起動で使うこと。
- SQL Server / LocalDB や Docker なしで動くこと。
- **EF InMemory や `:memory:` だけの成功は、この条件を満たしません。**

### 16. 新規DBと初期データ 【今回の追加要求】

- 移行後は**このサンドボックス専用の新規DB**を作ること。
- 旧SQL Serverデータの移送・旧DBとの共有は、今回の範囲に含みません。
- 初期データは**旧版ソースの7件（Active 6件、非Active 1件）**を使うこと。

### 17. DBの保存場所 【今回の追加要求】

- DBの保存場所は**1か所で設定**し、実行時に**絶対パスを確定**すること。
- 起動ディレクトリの違いで**別DBを暗黙作成しない**こと。
- パス構成は移行する人が決めます。参考例（**この形に従う必要はありません**）：`.local-data/bookcatalog.db`
- **起動出力で使用中のDBパスを確認できる**こと。
- Web公開フォルダ（公開される静的ファイルのルート）には置かないこと。

### 18. 再起動後の保持 【今回の追加要求】

- 書籍を追加・編集した後、**アプリプロセスを終了して同じDBで再起動**しても、
  編集結果と `CreatedDate` が保持されていること。

### 19. 通常起動でDBを作り直さない 【今回の追加要求】

- 通常の起動で**DBを削除・再作成しない**こと。
- 初期データは**最初の初期化で投入**し、利用者の変更・削除を取り消さないこと。
- **7件を全件削除した状態でも、通常の再起動で復活させない**こと。
  （旧版からの意図的な変更。上記「意図的に変える点」3を参照。）

### 20. 初期化とリセットの区別 【今回の追加要求】

- 「初期化」と「リセット」を区別すること。
- リセットは、**対象DBを表示する明示的な操作**にすること。
- リセットは**このサンドボックス用の指定DBだけ**を対象にすること。

### 21. DBファイルの分離 【今回の追加要求】

- リハーサル、本番デモ、受入テストは、それぞれ**別のDBファイル**を使うこと。
- **branch / tag を戻しても、DBファイルは戻らない**ことを説明に含めること。

### 22. スキーマ管理方式 【今回の追加要求】

- EF Core のスキーマ管理方式（Migrations など）は**移行する人が提案**し、**選択理由を記録**すること。
- **Migrations と `EnsureCreated` を同じDBの初期化に混用しない**こと。
- 採用した方法で、**初回作成・通常再起動・明示リセット**の3つが成立すること。

## D. 検証の証拠

### 23. テスト対象 【検証の証拠】

- テスト対象は、**このサンドボックスで移行したアプリ自身**であること。
- 起動したプロジェクト、URL、DBパス、対象コミットを記録すること。

### 24. 実際の操作と再起動 【検証の証拠】

- ビルド成功だけでなく、**実際のHTTP/UI操作**と**実プロセスの再起動**を確認すること。
- 無効値は**境界と境界超過**、任意項目は**未入力**を含めて確認すること。

### 25. 記録の内容 【検証の証拠】

- **確認手順・期待結果・実際の結果**を記録すること。
- **成功・失敗・未実施を区別**し、**未実施を成功扱いにしない**こと。

### 26. 自動テスト 【検証の証拠】

- 自動テストを作る場合は、**この受入条件から必要なもの**を作ること。
- 上流の完成版向けテストを**コピーしない**こと。
- テスト対象を完成例へ向けたり、**架空の実行ログを作ったりしない**こと。

## 移行する人が決めて記録する項目（この文書では決めない）

- .NET SDK / EF Core / SQLite provider の実際のバージョンと固定方法。
- EF Core のスキーマ管理方式とその理由。
- SQLite で採用する照合順序。
- DBファイルの具体的なパス構成。**例に従う必要はない。**
  保存場所を1か所で設定し、起動ディレクトリによって接続先が変わらないこと。
- リセット操作の具体的な操作方法（明示的で、対象DBを表示すること）。
- テストの範囲と手段。

## この文書に含めないもの

- 実装方法、完成コードの断片、完成版のファイル構成。
- 移行後のディレクトリ構成の正解。
- 上流の完成実装・既成の移行計画から取り込んだ内容。
